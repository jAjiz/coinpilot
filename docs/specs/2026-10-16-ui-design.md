# CoinPilot — Application Design

**Date:** 2026-10-16 · **Status:** draft, under review · **Scope:** Project 2, cycle 1 of 2

---

## 1. What this is

The application in front of the platform (project 1, [`2026-09-17-platform-design.md`](2026-09-17-platform-design.md)).
It does three things:

- **Onboarding.** Takes a new user from sign-in to a working configuration: Kraken key,
  portfolio targets, automation. This is the part that must feel obvious.
- **Looking.** Shows what the account is worth and how far it has drifted from its
  targets, without opening Kraken.
- **Deciding.** Shows a pending rebalance proposal and lets the user approve it.

The operator is the only user today, on a phone, through the deployment's private way in
(platform spec §13, §14). Nothing below assumes it: the application is multi-user because
the platform is.

### 1.1 Cycles

| Cycle | Delivers |
|---|---|
| **1 (this document)** | The application: onboarding, dashboard, proposal, history, settings |
| **2** | Notifications: Web Push for a pending proposal and for a failure streak |

Cycle 1 is useful on its own: a pending proposal is seen by opening the application.

### 1.2 Out of scope

Notifications (cycle 2). Charts of value over time. Live prices (platform spec §16,
Kraken WebSockets). Internationalisation: the interface is in English, like the
repository and the API.

## 2. Architecture

### 2.1 One origin

The platform serves the application. Both live at the same origin, so the session cookies
stay first-party and no CORS exists.

| Path | Served |
|---|---|
| `/api/*` | The API: every route of project 1 moves under this prefix, `/api/docs` and `/api/openapi.json` included |
| anything else | The application: a static file when one exists, `index.html` otherwise, so a deep link (`/settings`) survives a reload |

A path under `/api` that matches no route is a JSON `404`, never `index.html`.

Files with a content hash in their name are served with a one-year immutable cache.
`index.html` is served with `no-cache`, so a deploy reaches the browser on the next load.
The application is served with a strict Content-Security-Policy: same-origin resources
only, no inline script.

### 2.2 Build

The application is compiled where it is packaged. The `Dockerfile` becomes multi-stage:

1. A `node` stage runs `npm ci` and `npm run build` in `web/`, producing `web/dist/`.
2. The final stage is today's Python image, plus `COPY --from=<node stage> /web/dist web/dist`.

Node, `node_modules` and the TypeScript sources never reach the image. The release
pipeline, the deploy and the rollback are unchanged, and the application and the API in
an image always come from the same commit: a rollback takes both back together.

`web/dist/` is not committed.

### 2.3 Repository

The application lives in `web/` in this repository. A change that touches the API and the
application is one pull request, built and deployed as one image.

### 2.4 Stack

| Piece | Choice |
|---|---|
| Language and build | TypeScript, React, Vite |
| Routing | React Router |
| Server state | TanStack Query |
| API client | `openapi-typescript` types generated from `/api/openapi.json`, called through `openapi-fetch` |
| Styles and components | Tailwind CSS, shadcn/ui |
| PWA | `vite-plugin-pwa` |
| Decimal arithmetic | `big.js` |
| Tests | Vitest, Testing Library, MSW; Playwright for end to end |

**The generated client is the contract.** CI regenerates it from the API and fails when
the committed copy differs, so the application cannot drift from the API unnoticed.

### 2.5 Development

`npm run dev` serves the application on `http://localhost:5173` and proxies `/api` to
the platform on `http://localhost:8000`. Development is one origin too, so cookies behave
as in production. The development OAuth redirect URI becomes
`http://localhost:5173/api/auth/callback/google`.

## 3. Platform changes

One pull request, before any of the application, each change tested in the platform's
suite.

1. **The `/api` prefix** on every router. The cookie paths follow: the refresh cookie's
   becomes `/api/auth`, the login cookie's `/api/auth/callback`.
2. **The OAuth callback redirects.** On success it sets the cookies as today and answers
   `302` to `/`. On failure, `302` to `/login?error=<reason>`, `reason` being the message
   it returns today. It no longer returns the token pair in a body: no client reads it.
   `POST /api/auth/refresh` keeps accepting a body for a non-browser client.
3. **`/health` becomes `/api/health`.** Its callers follow: the `Dockerfile`
   `HEALTHCHECK`, the CI smoke test and `deploy.sh`.
4. **`onboarded_at`**, a nullable timestamp on the user's settings. An additive
   migration. `GET /api/config` returns it; `PATCH /api/config` accepts
   `"onboarded": true`, which sets it to now when it is null and leaves it otherwise.
5. **`PortfolioOut.holdings` is typed:** a list of `HoldingOut` (`asset`, `amount`,
   `price`, `value`, `managed`, `locked`, `target_pct`, `weight_pct`), every amount a
   decimal string or `null`, as the platform writes them today. A `dict[str, object]`
   generates no types.
6. **The application's files are served** as in §2.1, only when `web/dist/` exists. The
   platform's tests and a development run without a build see no change.
7. **The OAuth redirect URI** gains `/api` in `.env.example`, `env.production.example`
   and the runbook. It is changed in the Google OAuth client by hand, once.

## 4. Application structure

### 4.1 Routes

| Route | Screen |
|---|---|
| `/login` | Sign in with Google |
| `/onboarding/key`, `/onboarding/portfolio`, `/onboarding/automation`, `/onboarding/summary` | Onboarding (§5) |
| `/` | Dashboard (§6.1) |
| `/proposal` | Pending proposal (§6.2) |
| `/history` | History (§6.3) |
| `/settings` | Settings (§6.4) |

On a phone, a bottom bar with three tabs: Home, History, Settings. The proposal is reached
from the dashboard's card; it has no tab because it does not always exist.

### 4.2 Guards

Each navigation resolves, in order:

1. No session → `/login`.
2. `onboarded_at` is null → onboarding, at the first incomplete step: no key → `key`; no
   fiat or no asset → `portfolio`; otherwise → `automation`.
3. Otherwise → the route asked for. An onboarded user who opens `/onboarding` is sent to
   `/`.

### 4.3 Session

On load, `GET /api/auth/me`. Any `401` triggers `POST /api/auth/refresh` and retries the
request once. A refused refresh ends at `/login`.

**There is at most one refresh in flight.** Every request that meets a `401` while a
refresh is running waits for that refresh. Two refreshes with the same token end the
sign-in (platform spec §15), and the dashboard issues several requests at once, so
without this the user would be signed out every 15 minutes.

### 4.4 Source layout

```
web/src/
  api/            schema.d.ts (generated), client.ts (fetch, the single refresh)
  features/
    auth/         login, guards, session
    onboarding/   the four steps
    dashboard/
    proposal/
    history/
    settings/
  lib/            pure functions, unit tested
  components/ui/  shadcn/ui components
```

### 4.5 What `lib/` owns

The logic the application adds to the API, each piece a pure function:

- **Cadence translation** between the form (§5.3) and the platform's fields, both ways.
- **Summary sentences** from a configuration (§5.4).
- **Prefill weights** from a portfolio read (§5.2).
- **Account totals**: managed, unmanaged, total (§6.1).
- **Amount formatting.** The platform sends amounts as decimal strings. They are added
  with `big.js` and formatted as text; an amount is never a JavaScript `number`.

## 5. Onboarding

A linear wizard, shown once. Each step explains what it does and offers defaults.
Afterwards each block is edited on its own in Settings.

### 5.1 Key

- How to create the key in Kraken, with the four required permissions as a checklist
  (`query-funds`, `modify-trades`, `query-open-trades`, `query-closed-trades`, platform
  spec §5.2) and a prominent "never enable withdrawal permissions".
- Key and secret fields; **Verify & save** calls `POST /api/credentials`.
- Refused: the platform's reason, verbatim.
- Accepted: the unnecessary permissions it names, with the recommendation to turn them
  off, and the recommendation to restrict the key to the server's IP address.

### 5.2 Portfolio

- **Fiat first**, with "cannot be changed later". Saved with `PATCH /api/config`.
- **The account, prefilled.** `POST /api/portfolio/refresh` reads every balance and
  prices the unconfigured ones against the fiat. Each tradable asset is listed with its
  value and its current weight, a **Manage** switch (on) and a target prefilled with that
  weight. Locked balances are listed but cannot be managed.
- **Prefill weights** are each asset's value over (sum of priced asset values + cash),
  rounded down to one decimal place, so they never sum above 100. Leaving them unchanged
  makes the first rebalance find nothing to do. An asset with no price against the fiat
  is listed without a weight and cannot be managed.
- **Cash target** below: 100 minus the targets, recomputed as the user types. Above 100
  is an error on the form.
- **Add asset** for one the account does not hold yet. The pair is validated when the
  step is saved, by `PUT /api/assets/{asset}`.
- Saving writes one `PUT` per managed asset.

### 5.3 Automation

**Invest cadence**: a select and a start date.

| Option | Platform fields | Start date |
|---|---|---|
| As soon as possible (every 15 min) | `MIN` | hidden: below a day the anchor is ignored |
| Daily | `INTERVAL`, 1 day | the first day |
| Weekly | `INTERVAL`, 7 days | its weekday is the day of the week |
| Monthly | `INTERVAL`, 1 month | its day is the day of the month; the 29th to 31st fall on a shorter month's last day (the platform does this) |

**Rebalance cadence**: the same shape.

| Option | Platform fields |
|---|---|
| Monthly | `INTERVAL`, 1 month |
| Quarterly | `INTERVAL`, 3 months |
| Half-yearly | `INTERVAL`, 6 months |
| Yearly | `INTERVAL`, 12 months |

There is no "as soon as possible" for rebalancing. A rebalance can always be requested
from the dashboard.

**The anchor** is the chosen date at **12:00 in the browser's time zone**, converted to
UTC. The platform spreads users over the hour after it (platform spec §10.2), so a run
falls between 12:00 and 13:00: an hour a notification is welcome. Stored in UTC, it moves
an hour with daylight saving time, as the platform spec accepts (§3.5). The date defaults
to today.

A configuration the select cannot express (one made through the API) is shown as
"Custom" with its fields read-only, and is kept unless the user picks an option.

**Switches and thresholds**

| Field | Control | Default in the wizard |
|---|---|---|
| `invest_cash_enabled` | Invest free cash automatically | off (platform spec §3.4) |
| `cash_rebalance_enabled` | When investing, buy the most underweight assets first | off |
| `auto_rebalance_enabled` | Rebalance automatically, without asking | off |
| `min_drift_pct` | Rebalance only when an asset drifts more than … % | 5.0 |
| `min_order_fiat` | Skip orders smaller than … (Kraken's own minimum always applies) | 0 |

Each control carries one sentence saying what it changes.

### 5.4 Summary

The configuration in sentences, for example: *"Every Monday at 12:00, free EUR is
invested toward your targets. On the 1st of every quarter, if any asset has drifted more
than 5 %, a rebalance is proposed for you to approve."* Below it, the first run of each,
from the `next_invest_at` and `next_rebalance_at` the platform computed: a start date of
today whose 12:00 has passed begins at the next occurrence, and the user sees which.
**Start** sends
`PATCH /api/config` with `"onboarded": true` and opens the dashboard.

## 6. Screens

### 6.1 Dashboard

- **Total value** of the whole account, and below it "managed X · unmanaged Y", the time
  of the read, and a refresh button (`POST /api/portfolio/refresh`).
- **Allocation**: one row per managed asset and one for cash. A bar of the real weight
  with a mark at the target, and the drift in points. Rows above `min_drift_pct` are
  highlighted.
- **Proposal card**, when there is a live proposal: number of orders, total amount,
  **Review**.
- **Invest now**: first `POST /api/invest?preview=true`, showing the orders Kraken
  validated, then a confirmation that sends `POST /api/invest`.
- **Rebalance now**: `POST /api/rebalance`, which creates or refreshes the proposal and
  sends nothing.

### 6.2 Proposal

Every leg with side, asset and amount. Skipped legs are shown with their note (below
Kraken's minimum, for example). **Approve** sends the version on screen. A version
conflict reloads the proposal with "The proposal changed; review it again". **Dismiss**
calls `DELETE /api/proposal`.

### 6.3 History

`GET /api/sessions`: date, operation, trigger (scheduled or manual) and status. Expanding
one shows its log messages and the orders it placed (`GET /api/orders`).

### 6.4 Settings

The onboarding blocks, each editable on its own: portfolio targets, automation. The key's
status, replace and delete. **Pause everything** (`paused`). **Sign out**.

## 7. Errors and states

Every screen that loads data has three states: loading (skeletons in the shape of the
content), empty (a sentence saying why) and error (a message and a retry button).

| Platform answer | Meaning | The application |
|---|---|---|
| `401` | The access token expired | The single refresh, then one retry; `/login` if refused |
| `409` on invest or rebalance | An evaluation is running (platform spec §9.6) | "An operation is already running; try again in a moment" |
| `409` on approve | The proposal's version changed | Reload it and ask for a new review |
| `422` | Validation | The message next to the field that caused it |
| `503` | Kraken did not answer; nothing was recorded | "Kraken didn't answer; nothing was changed", with retry |
| no network | The phone is offline | A persistent offline notice; buttons that send are disabled |

**Actions that move money** (invest, approve) always show what they will do first and
take a second tap to confirm. The button is disabled while the request is in flight, so a
double tap never sends twice; the platform's lock is not the only guard.

**The service worker caches the application shell only**, never an `/api` response. An
old portfolio is never shown as a current one.

## 8. Testing

- **Unit (Vitest), `lib/`:** cadence translation both ways, including the 31st, a
  daylight-saving change, a date in the past and a "Custom" configuration; prefill
  rounding never summing above 100; summary sentences; amount formatting and totals.
- **Components (Testing Library, MSW for the API):** each onboarding step and its errors;
  the single refresh under several simultaneous `401`s; the version conflict on approve;
  the double-tap guard.
- **End to end (Playwright), one journey:** sign-in → onboarding → dashboard, against the
  mocked API. Neither Google nor Kraken is called, as the platform's tests place no real
  order.
- **Platform:** each change in §3, including that an unknown `/api` path is a JSON `404`
  and a deep link is `index.html`.
- **CI** gains a job for `web/`: lint, type check, tests, build, and the generated-client
  check (§2.4).

## 9. Delivery

Each step is a pull request that works on its own.

1. **Platform changes** (§3). After it, the API answers under `/api` and the callback
   redirects to a page that does not exist yet.
2. **`web/` skeleton:** Vite, the generated client, session and guards, the multi-stage
   `Dockerfile`, the CI job. Deployed, it signs in and shows an empty page.
3. **Onboarding.**
4. **Dashboard and proposal.**
5. **History and settings.**

## 10. Design choices

- **The platform serves the application.** No third container and no Node on the host;
  the application and the API ship and roll back as one image. The cost is the `/api`
  prefix, a one-time change with a single client.
- **A wizard, not a checklist.** The steps have an order: no portfolio without a key, no
  automation without a portfolio. A wizard says so, and keeps the dashboard from being
  shown half-empty.
- **Prefilled from the account, not blank.** The user starts from what they hold, and
  keeping today's weights is the safe default: nothing is sold by surprise.
- **Plain-language cadences, not the platform's fields.** An anchor is an implementation
  term. The select covers the cadences a person asks for; the platform keeps the rest
  reachable through the API.
- **Rebalancing has no "as soon as possible".** A rebalance sells, so it is looked for on
  a calendar the user chose, and requested by hand in between.
- **`onboarded_at`, not an inference.** The settings always have defaults, so "reviewed
  the automation" cannot be told apart from "closed the app at step 2" without a field.
- **Amounts stay decimal strings.** The platform never writes an amount as a float; the
  application does not either.
